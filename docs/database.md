# Database

Cloudflare D1 (SQLite) schema for SPILL. Source of truth: `api/schema.sql`. Data access goes through the single-file Worker API in `api/worker.js` (see `api/DEPLOY.md`); the Next.js app never talks to the database directly.

## Entity-relationship summary

```
admin_users 1 ──── n admin_sessions
discussion_sessions 1 ──── n submissions
discussion_sessions 1 ───── 1 presentation_state ──> submissions (current, nullable)
```

- `discussion_sessions` — one church discussion event, joined by an 8-character `public_code`.
- `submissions` — participant contributions to a session. Cascade-deleted with the session.
- `admin_users` — one row per admin/moderator, with a PBKDF2 password hash. The `email` column is only an internal placeholder (`admin@spill.local`), never user input. There is no public sign-up.
- `admin_sessions` — login tokens for admins (issued by the Worker on login, stored as `token` primary key, expire after 7 days).
- `presentation_state` — the projector's pointer: which submission is currently on screen for a session.

## CHECK constraints (text columns standing in for enums)

| Column | Values |
|---|---|
| `discussion_sessions.status` | `draft`, `live`, `paused`, `closed` |
| `submissions.category` | `question`, `opinion`, `challenge`, `twocents` |
| `submissions.moderation_status` | `pending`, `approved`, `hidden` |
| `admin_users.role` | `admin`, `moderator` |

`is_pinned` and `hidden_from_presentation` are `INTEGER` 0/1 columns. Fixed contract values other parts of the app depend on: `public_code` is 8 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no `0`/`O`/`1`/`I`/`L`), stored uppercase (CHECK-enforced via a single negated GLOB class - SQLite rejects the 8x repeated-class form as "pattern too complex" at INSERT time). Content and nickname limits are trimmed lengths (1–1000 chars for content, 1–60 for nickname, 1–200 for title); the Worker validates before insert, the CHECKs are a backstop. All timestamps are ISO-8601 `TEXT` (UTC, `strftime('%Y-%m-%dT%H:%M:%fZ')` defaults); `updated_at` is maintained in Worker code, not triggers.

## Indexes

| Index | Rationale |
|---|---|
| `submissions (session_id, created_at desc)` | main feed ordering per session |
| `submissions (session_id, moderation_status)` | moderation queue and approved-only public reads |
| `submissions (session_id, category)` | category filtering |
| `submissions (session_id, participant_id)` | duplicate suppression and per-participant lookups |
| partial `submissions (session_id) where is_pinned = 1` | fast lookup of a session's pinned submission |
| unique partial `discussion_sessions (status) where status = 'live'` | **single-live-session rule**: at most one row may be `live`, even under concurrent publishes. `POST /admin/sessions/:id/status` in the Worker also checks inside a transaction; the index is the final guarantee. |
| `admin_sessions (user_id)` | admin session lookups by user |

## Applying the schema

```bash
cd api
npx wrangler d1 execute spill --remote --file schema.sql
```

Written to be safe to re-apply (`CREATE TABLE/INDEX IF NOT EXISTS`). Local development uses `--local` against the `wrangler dev` database.

## Provisioning the first administrator

There is **no public registration** in the app. Two documented paths:

1. **Bootstrap env**: set the Worker secret `SPILL_ADMIN_PASSWORD` (`npx wrangler secret put SPILL_ADMIN_PASSWORD -c wrangler.toml`; `SPILL_ADMIN_PASSWORD` in `api/.dev.vars` for local dev). No default password ships, so login always fails until the secret is set. The first time `/admin/auth/login` runs with an empty `admin_users` table, the Worker seeds one admin (role `admin`, placeholder email `admin@spill.local`) before checking the submitted password. A password matching the secret is accepted via constant-time comparison; when the secret matches but the stored hash differs, the Worker re-hashes and updates the row, so changing the secret rotates the stored hash on the next successful login.
2. **Manual insert**: insert an `admin_users` row directly (`npx wrangler d1 execute spill --remote --command "..."`), hashing the password in the `pbkdf2$<iterations>$<salt-hex>$<hash-hex>` format above.

Role values are `admin` and `moderator`. Every admin route checks the caller's `admin_sessions` token server-side; creating the auth user alone grants nothing. To revoke access, delete the `admin_users` row (its `admin_sessions` rows cascade) or delete rows from `admin_sessions` to force re-login.
